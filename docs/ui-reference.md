# UI Reference

元のGoogleスプレッドシートUIを参考にした画面設計メモです。

## 基本方針

既存運用は、フォーム中心ではなく横長の台帳グリッド中心です。Next.js側も、最初の主画面は「一覧テーブル + 固定ヘッダー + 横スクロール + セル編集」を軸にします。

## 観察したUI

### 古物台帳

- 元シートには `古物台帳`, `EC販売`, `仕入れ表`, `為替レート`, `(古物台帳) オーダー`, `(販売) ペイメント`, `仕入れ元データ` のタブがある
- アプリUIでは、重複の多い `仕入れ表` と `仕入れ元データ` を `仕入れ管理` として統一する
- 上部の複数行は、グルーピングとヘッダーに使われている
- 受入れと払出しが同じ行に横並びで表示される
- 受入れ、払出し、販売先・買主由来などの列グループが色で分かる
- 重要な横グループ:
  - 受入れ
  - 取引した古物
  - 確認方法 取引ID
  - 取引きの相手方
  - 払出し
  - 販売先
  - 買主住所
- セルには `在庫`, `仕入れ無`, `本人確認済み` のような運用ステータスが直接入る
- 赤背景の行・セルは要確認やマスク済み住所など、注意状態を表している

### 仕入れ元データ

- 仕入れ元データは、実務上は販売・発送・梱包情報も含む
- SKU、eBay Order No、販売日、仕入日、国、販売額、仕入れ、送料、梱包者、発送サイト、重量、サイズ、商品名、仕入先が横並び
- CSV名だけでテーブルを決めるのではなく、ヘッダー行からデータ種別を判定する必要がある

### 仕入れ管理フォーム

仕入れ管理は `wp_kobutsu_supplier_sources` を単一の保存先にします。簡易入力と詳細入力でテーブルを分けず、未入力の詳細項目は空欄、0、NULLとして同じレコードに保持します。

SKUは仕入れ管理原票の一意キーとして扱います。同じSKUを入力して保存した場合、確認表の行は増えず、既存行が更新されます。

フォームは入力負荷を下げるため、次の3区分で表示します。

必須入力:

- SKU
- Order no.
- 仕入日
- 仕入先
- 仕入金額
- 商品名

よく使う入力:

- アカウント
- 販売日
- 国
- 販売額
- 送料
- 発送サイト
- 梱包者
- 備考

詳細入力:

- MAG
- ポイント加算
- 実重g
- 体積重g
- 縦cm / 横cm / 高さcm
- 初回メール
- 領収書印刷日

## Next.js UIへの反映

### 第一画面

第一画面はダッシュボードではなく、古物台帳グリッドにします。

必要な機能:

- タブ切り替え: `古物台帳`, `仕入れ管理`, `EC販売`, `為替レート`, `ペイメント`
- 固定ヘッダー
- 横スクロール
- 列グループの色分け
- SKU、注文番号、商品名、仕入先、buyer IDで検索
- ステータス/要確認フィルタ
- CSV取込結果のエラー行レビュー

### 編集方式

初期実装では、スプレッドシート風のインライン編集を目指します。ただし一括保存ではなく、行単位の保存を基本にして、台帳としての更新履歴を残せるようにします。

### 色の意味

- 緑: 自動入力、CSV/連携由来
- オレンジ: 手動入力または確認が必要な業務項目
- 紫: eBay/Shopeeなど販売先・買主由来
- 赤: 要確認、取込異常、欠損、マスク済み、整合性エラー

## CSVインポートへの影響

このUIではヘッダーが複数段あり、実データ開始行が固定ではありません。インポート処理は以下を必須にします。

- 空行と注釈行をスキップ
- 複数行ヘッダーを解釈
- 必須列の組み合わせでCSV種別を判定
- 列番号ではなく列名でマッピング
- 取込前プレビューで「どの列をどのDB項目に入れるか」を表示
- 取込できない行を赤表示でレビューできるようにする
